## Rules and evidence

- **Read-only toward real users and services.** Work on a fresh, signed-out disposable emulator. No accounts/OAuth, sync, feedback submissions, social posts/reactions, sharing, external links, ads, purchases, update installs, or trip/background alerts. Apart from setup, one test favorite and a reversible in-app theme change (below), use only navigation, search and transient selections. Searches may leave local history. Never touch pre-existing favorites, clear data, reinstall, change OS settings, edit the app or query APIs directly. If an account is signed in, skip the local-write scenarios; never capture personal information.
- **One short journey per persona.** Obey the supplied `MAX_ACTIONS` (default 15 UI actions, never above 40); count each tap, swipe, Back, permission response and text entry. Spend the first few actions reaching Bus home, most of the rest on one path below. A small limit may cover only setup. With time left, try one adjacent path, not every city, mode or permutation. A brief wait and **one** retry or alternate query is enough; if still blocked, capture the state and move on or report. Do not spend the budget refreshing live services.
- Capture the initial screen with `python3 scripts/android/screen.py results/<persona> 01` (substitute the actual id). After **every** UI action, capture the next `02`, `03`, … and **Read the PNG** and inspect the element list before acting again. Capture loading and settled states separately if needed. Element centres are real pixels; double coordinates read from the half-size PNG. Never reuse a number. A missing tree node or emulator crash-log notice alone does not establish an app failure.
- Use `python3 scripts/android/action.py` with **one** of: `tap X Y`, `swipe X1 Y1 X2 Y2 [ms]`, `back`, `type "text"` (focused field), or `relaunch` (stops and reopens YABus with its data intact). Each counts as one action. No raw ADB, settings/airplane-mode toggles or other shell workarounds. Screenshots and writing the report are not UI actions.

## Deliverables (even if blocked)

Write only `results/<persona>/report.md` and `results/<persona>/findings.json` with the runner's Write tool; keep numbered PNGs beside them. No issue filing, public uploads or raw device logs.

1. **report.md**: five-line summary: device/persona + locale/font/theme; goal; initial permission/region/DB state; outcome; actions used/limit. List coverage as **observed** (screen IDs), **attempted but blocked** (last screen + reason) or **not attempted** (budget/scope). For each issue, most severe first: screen, short repeatable steps, expected vs actual, task impact, severity and screenshot numbers. Quote the relevant UI text. Separate environment/data limitations from reproducible app defects. End with the persona's keep/not-keep verdict and score /10.
2. **findings.json**: valid JSON object with numeric `score` (0–10) and `issues` array. For **every** issue supply a precise `title`, `severity` (`blocker`, `major`, `minor` or `cosmetic`), `screen` (page name), `steps` (nonempty array of nonempty reproduction strings), `screens` (nonempty array of existing two-digit IDs such as `["04","05"]`, not paths). Use the same issue titles, severity, evidence and score in both files. `issues: []` is correct when there are no verified defects; still report the journey, screenshots and gaps. Never invent a finding or claim coverage for an unvisited screen.
